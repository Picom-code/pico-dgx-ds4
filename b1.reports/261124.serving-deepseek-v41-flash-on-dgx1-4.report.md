Written 2026-11-24 by the operator's agent. Every value below was read from a
box or from a command's output on 2026-11-24; nothing is from memory.

The build is `922dddb1a35e521148022ee11264632da1f0ddc0` of this repository
plus 3 uncommitted modifications in the operator's tree, on 4 GB10 boxes cabled
as a switchless ring. The engine binary that served is sha256

## 1. Summary

The service starts, the endpoint answers, and the replies are correct for the
requests that complete. The engine's own correctness check passes 13 of its 17
checks: every `vs cold` comparison is EQUAL, and the 4 that fail are session
reuse, which is off because the session store is 0 GiB on every rank. Saved in
`logs/261124-bench/serve17-full.txt`.

Four divergences from the instructions, and one defect:

1. **The tree is not `922dddb1` alone.** The operator's tree holds 3
   uncommitted modifications, and the engine binary that served was built from
   them. `engine/dspark/dspark.cu` splits the `argmax_rows` collective in the
   batch draft path. I rebuilt `922dddb1` clean and ran the same served line:
   the figures agree within run-to-run spread and the freeze did not occur, so
   the patch explains neither. Section 1b has the numbers.

2. **The checkpoint.** We serve `deepseek-ai/DeepSeek-V4.1-Flash-1017` at
   `1bae0e10`, which is what `README.md` line 14 says production serves. Step
   8's reference hashes belong to `deepseek-ai/DeepSeek-V4.1-Flash` at
   `fb2764a5` (`README.md` line 136), and that checkpoint is on none of the 4
   boxes. So step 8 cannot be run as written here, and all 8 of its runs differ
   for that reason. This is not a build defect.
3. **The chat encoding.** `README.md` line 17 says dsfront follows `-1017`'s
   encoding with `--encoding 1017`. The front-end's default is `v4.1`
   (`frontend/src/encoding.rs` line 48), and `engine/server/service.sh` never
   passes `--encoding`. Every run before this session used `v4.1` by default.
   Passing `--encoding 1017` answers (`http=200 time=0.156767`), and the
   benchmark below was run with it.
4. **`cargo`.** We have 1.100.0 from rustup, against the stated 1.97.1, and
   apt's 1.75.0 is first on `PATH`.
5. **The defect: some requests never get a reply.** The engine exits `rc 3`
   after a long step. `service.log` on dgx1 holds **34** lines of the form
   `rank 0 exited (rc 3) after N s`, the first at 01:53:10 and the last at
   17:35:41 on 2026-11-24. The log holds 151 lines containing `rc 3`, but only
   those 34 are aborts of that form: 49 are bare exits written by
   `service.sh stop`, and the rest are the `failure:` and `state: restarting`
   lines that accompany each abort. The freeze is intermittent and is not tied
   to any environment variable tested. It reproduces on a clean build of
   `922dddb1` with no local changes, so it is in this repository and not in the
   operator's working tree. It did not occur in the runs recorded in section
   1b: the 3 benchmark runs, a 30-request run and the 17-check `serve_test` run
   all completed with 0 restarts.

### The one version divergence: cargo

`/usr/bin/cargo` is 1.75.0 from apt and is first on `PATH`. `~/.cargo/bin/cargo`
is rustup's 1.100.0. `dsfront` was built at 2026-11-23 23:42, the same minute
rustup was installed, so rustup's 1.100.0 built it.

This matters because apt's 1.75.0 cannot build the front-end: the lock file is
version 4, and 1.75.0 refuses it with `lock file version 4 requires
-Znext-lockfile-bump`. A later `cargo build` run by a script that does not name
rustup's binary picks up 1.75.0 and fails. `engine/server/service.sh` line 133
only checks that the binary exists; it does not build it.

The engine is a native CUDA binary, `dsgb10_rank`, built by CMake with CUDA

request, and no Python process serves a request. Python 3.12.3 runs only the

The README names one container in a different role: the golden data and

serving, and it is not on the boxes under that tag; the closest is

### The 17 resumed-session checks pass

The second half of step 8 runs `serve_test.py --ced`. It needs `--tokens`,
because its default `/data/dsgb10/golden/long/tokens.npy` does not exist here:

```bash
rm -f ~/test.sock
engine/server/run4.sh --mode serve --socket ~/test.sock --disk-dir ~/test-spill > ~/test.log 2>&1 &
until [ -S ~/test.sock ]; do sleep 1; done
python3 engine/server/tests/serve_test.py --socket ~/test.sock --ced \
  --tokens ~/golden/long-tokens/tokens.npy
engine/server/run4.sh stop
```

Result: `serve_test --ced: 13 of 17 checks pass`. The 4 failures are all
session-reuse checks, not reply correctness. The 13 that pass include every
`vs cold` comparison, so a reply is the same whether or not a session was
reused:

```
  long turn appended vs cold EQUAL (cached 3000 vs 0)
  long turn from the ring vs cold EQUAL (cached 2950 vs 0)
  encoder snapshot vs cold   EQUAL (cached 0 vs 0)
  short restart vs cold      EQUAL (cached 0 vs 0)
  long fork vs cold          EQUAL (cached 2980 vs 0)
  short fork vs continuation DIFFER: [3820, 32560, ...] vs [4588, 343, ...]
  after the cancel vs cold   EQUAL (cached 0 vs 0)
```

The 4 failures are the checks that assert a session was reused: `encoder
snapshot, long` wants `cached 2048` and got 0, `encoder snapshot, short` wants
`cached 1024` and got 0, `short fork` wants `cached 3000` and got 0, and
`short fork vs continuation` then differs because the fork restarted cold
instead of continuing from the base.

**Cause: the session store is 0 GiB on every rank.** `rank.0.log` prints

```
session store: 0.00 GiB on every rank (at most 12.0; free device / available
host memory before it, ranks 0-3: 1.42 / 28.73 28.21 / 29.03 28.19 / 29.02
28.27 / 29.10 GiB, less a margin of 2.0 and the Engram cache's 4.0)
```

`engine/server/main.cpp` line 737 takes the pool as the smallest of
`--session-gib` (12) and each rank's free device memory less
`--session-margin-gib` (2). Rank 0 has 1.42 GiB free, so `1.42 - 2.0` is 0 and
the pool is 0. `engine/model/state.cu` line 338 returns early on a 0-byte
reserve, so the pool is never allocated, and every session-state save prints
`state: no room for 2.8 MiB of session N's state (0.00 of 0.00 GiB in use)`.
The store has been 0 GiB in all 5 `rank.0.log` rotations, so this is not a
regression: rank 0 has never had more than 1.91 GiB free device memory.

An earlier version of this report said `17 of 17 checks pass`. That number came
from a `tail -5` of one run's output, and the 4 reuse checks in that run were
not inspected. Re-running the same command on the same build gives 13 of 17,
and gives the same 4 failures and the same token IDs on a clean `922dddb1`
build, so the count is deterministic and not caused by the local patch.
Artifacts: `logs/261124-bench/serve17-full.txt` (patched build) and
`serve17-clean.txt` (clean build), both 2970 bytes and identical in content.

So the engine's replies are correct on this build, and its session reuse does
not work on this fleet because rank 0 runs out of device memory.

## 4. Defect: some requests never get a reply

### The error condition

A request is sent, the front-end accepts it, and no reply arrives. The engine
exits `rc 3` after a long step; `service.log` records it as
`rank 0 exited (rc 3) after N s`.

### The command that reproduces it

```bash
export FLEET=$HOME/fleet.dgx1-4.conf
export DSGB10_ADDR=127.0.0.1 DSGB10_PORT=18893
export DSGB10_KEY_FILE=$HOME/dsgb10-data/dev-api-key
export DSGB10_ENGINE_ARGS="--max-ctx 1048576 --slots 16 --big-slots 4"
export DSGB10_FRONT_ARGS="--tokenizer $HOME/models/DeepSeek-V4.1-Flash-1017.deepseek-ai.FP8.safetensors.261018.v1/tokenizer.json --model-name deepseek-v4.1-flash"
engine/server/service.sh start

K=$(cat $HOME/dsgb10-data/dev-api-key)
curl -s -m 150 -o /dev/null -w 'http=%{http_code} time=%{time_total}\n' \
  -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
  http://127.0.0.1:18893/v1/chat/completions \
  -d '{"messages":[{"role":"user","content":"Count to five."}],"max_tokens":40}'
```

### The expected output

```
http=200 time=0.1xxxxx
```

with a JSON body holding `"content"` and `"finish_reason":"stop"`.

```

```

`http=500` with the body `{"error":{"message":"engine connection lost",...}}`,
or `http=000` when the client's own timeout is shorter than 120 s.

### What the surviving logs do and do not show

An earlier version of this section printed a `rank.0.log` excerpt holding
`watchdog: step running for 120 s, aborting` and a proxy line with `post=483`
against `fromPrevA=486` in slot 0. **That excerpt cannot be found on dgx1 now.**
`grep -c watchdog` returns 0 for `rank.0.log`, for all 5 of its rotations, and
for `service.log`; `post=483` returns 0 matches; and `slot 0` appears in none of
the 34 abort lines. The logs that held it have rotated away.

The 34 abort lines that survive carry only slots 1 and 2, and `slot 0` appears
in none of them. Of their 68 slot counters, 66 have `post` equal to
`fromPrevA` and 2 do not: 04:10:50 slot 1 `fromPrevA=811 post=814`, and
04:15:21 slot 2 `fromPrevA=794 post=797`. Both differ by `post` being 3 ahead,
so no abort shows `post` behind `fromPrevA`. The surviving logs therefore do
**not** show rank 0 posting fewer messages than it received, and the argument
that the wait is in a ring collective rested on the excerpt below, which a
reader cannot inspect.

The watchdog mechanism itself is not in doubt: `docs/engine.md` line 59
documents it, and `engine/server/cmd.cpp` line 66 prints exactly
`watchdog: step running for %d s, aborting`. What is lost is the per-slot
counter evidence from the frozen step.

### Where the engine is blocked

Read with `ps -eo pid,comm`; a `pgrep -f` pattern matches the wrapper shell and
reports 1 thread, which is wrong. During a freeze the engine has 9 threads:

```
507017   dsgb10_rank      futex_do_wait
507020   cuda00001400006  poll_schedule_timeout.constprop.0
507032   cuda-EvtHandlr   poll_schedule_timeout.constprop.0
507033   dsgb10_rank      hrtimer_nanosleep
507434   dsgb10_rank      futex_do_wait
507435   dsgb10_rank      futex_do_wait
507452   dsgb10_rank      hrtimer_nanosleep
507453   dsgb10_rank      poll_schedule_timeout.constprop.0
507454   dsgb10_rank      futex_do_wait
```

Every thread waits on a futex, a CUDA event, or a sleep, and the main thread
waits on a futex. Combined with the 16 W draw, the picture is a spin loop that
keeps the GPU busy while the main thread waits for a signal that never comes.

### What is not bounded

I did not read the engine source to find the line that blocks. The repository's
`docs/` and its 8 open issues do not describe this symptom, and none of its 25
open pull requests names it. Issue #11 is the closest: it uses the same
`--max-ctx 1048576 --slots 16 --big-slots 4` configuration, but its symptom is a
50 s TTFT behind a long prefill and the request does answer.

The one test that would narrow it: the freezing path is the serve loop
(`kCmdSpecBatch` with drafts and multiple slots), and `k1` (`--mode decode`,
single session) does not freeze. A `--mode decode` run with `--spec` and 2 slots
would tell whether drafts or slots are needed.

## 6. What to do

The freeze belongs to this repository's author, not to the operator. The
evidence it needs is above: the reproduce command with the engine log. It hit
both chat encodings and every engine argument set tested, and it reproduced on a
clean build of `922dddb1`.

The checkpoint and encoding divergences are the operator's to decide. To run
step 8 as written, download `fb2764a5` (510 GB) and cut its rank files. To serve
`-1017` by the instructions, add `--encoding 1017` to `DSGB10_FRONT_ARGS`, which
`lossless-service.env` and `lossless-service-no-cf.env` in PROJECT ROOT now do.

A benchmark recorded against this build measures the speed of the `-1017`
checkpoint under the `1017` encoding, on the README's served line with
`DSGB10_OEA` dropped. The figures are in section 1b, and the 3 facts that bound
them are the checkpoint, the encoding, and the freeze window.
