# Serving DeepSeek-V4.1-Flash-1017 on dgx1..dgx4: what the instructions produced

Written 2026-11-24 by the operator's agent. Every value below was read from a
box or from a command's output on 2026-11-24; nothing is from memory.

The build is `922dddb1a35e521148022ee11264632da1f0ddc0` of this repository, on
4 GB10 boxes cabled as a switchless ring. The instructions followed are
`ds41f-4xgx10-switchless/README.md`, section "run it", steps 1 to 9.

## 1. Summary

The service starts, the endpoint answers, and the replies are correct for the
requests that complete. The engine's own correctness check passes: the 17
resumed-session checks of step 8 give `17 of 17 checks pass`.

Three divergences from the instructions, and one defect:

1. **The checkpoint.** We serve `deepseek-ai/DeepSeek-V4.1-Flash-1017` at
   `1bae0e10`, which is what `README.md` line 14 says production serves. Step
   8's reference hashes belong to `deepseek-ai/DeepSeek-V4.1-Flash` at
   `fb2764a5` (`README.md` line 136), and that checkpoint is on none of the 4
   boxes. So step 8 cannot be run as written here, and all 8 of its runs differ
   for that reason. This is not a build defect.
2. **The chat encoding.** `README.md` line 17 says dsfront follows `-1017`'s
   encoding with `--encoding 1017`. The front-end's default is `v4.1`
   (`frontend/src/encoding.rs` line 48), and `engine/server/service.sh` never
   passes `--encoding`. Every run in this report therefore used the `v4.1`
   encoding, not `-1017`'s. Passing `--encoding 1017` was tested and answers
   (`http=200 time=0.156767`), but every benchmark attempt with it froze on the
   first request, so no figure exists for it.
3. **`cargo`.** We have 1.100.0 from rustup, against the stated 1.97.1, and
   apt's 1.75.0 is first on `PATH`.
4. **The defect: some requests never get a reply.** The engine's own watchdog
   aborts the step at 120 s and rank 0 exits `rc 3`. The freeze is intermittent
   and is not tied to any environment variable tested. It reproduces on a clean
   build of `922dddb1` with no local changes, so it is in this repository and
   not in the operator's working tree.

### The checkpoint

`README.md` line 136 states which checkpoint step 8 checks:

> The checkpoint, deepseek-ai/DeepSeek-V4.1-Flash at revision `fb2764a5`:
> measurements from 2026-10-13 on use it, and **step 8's hashes are its**.

`README.md` line 14 states which checkpoint production serves:

> Since 2026-10-18 11:56 production serves DeepSeek-V4.1-Flash-1017 at
> `1bae0e10`, deepseek-ai's update with the same architecture, config, tokenizer
> and tensors and **new values in every shard, the Engram tables included**.

We serve the second. The model card on dgx1 reads
`# DeepSeek-V4.1-Flash-1017`, shard 1 hashes to `13bd121075f0b68c`, and
`~/dsgb10/weights/rank0.dsw` names
`DeepSeek-V4.1-Flash-1017.deepseek-ai.FP8.safetensors.261018.v1` in its header.

`ls -d ~/models/*` on all 4 boxes lists only the `-1017` tree. There is no
`DeepSeek-V4.1-Flash` tree and no `weights-official` directory on any box. So
step 8 as written needs a 510 GB download of `fb2764a5` and a fresh cut of its
rank files.

### The chat encoding

`README.md` line 17 says dsfront follows `-1017`'s chat encoding with
`--encoding 1017`. `frontend/src/encoding.rs` line 48 marks `V41` as
`#[default]`, and `frontend/src/main.rs` line 18 states `v4.1` is the default.
`engine/server/service.sh` contains no `encoding` line, so the flag is never
passed and every run in this report used `v4.1`.

Passing it works. With `DSGB10_FRONT_ARGS` ending `--encoding 1017`, the
front-end's command line holds `--encoding 1017` and a request answers:

```
encoding1017 http=200 time=0.156767
"finish_reason":"stop"
```

But the benchmark could not be recorded under it: 4 attempts each froze on the
first decode request, with `rank 0 exited (rc 3)`. The service log held 95
`rc 3` restarts by 16:22:39. So the freeze is independent of the encoding.

### The one version divergence: cargo

`/usr/bin/cargo` is 1.75.0 from apt and is first on `PATH`. `~/.cargo/bin/cargo`
is rustup's 1.100.0. `dsfront` was built at 2026-11-23 23:42, the same minute
rustup was installed, so rustup's 1.100.0 built it.

This matters because apt's 1.75.0 cannot build the front-end: the lock file is
version 4, and 1.75.0 refuses it with `lock file version 4 requires
-Znext-lockfile-bump`. A later `cargo build` run by a script that does not name
rustup's binary picks up 1.75.0 and fails. `engine/server/service.sh` line 133
only checks that the binary exists; it does not build it.

### No container and no PyTorch in the serving path

The engine is a native CUDA binary, `dsgb10_rank`, built by CMake with CUDA
13.0's `nvcc`. The front-end is a Rust binary, `dsfront`. No container serves a
request, and no Python process serves a request. Python 3.12.3 runs only the
helper scripts.

The README names one container in a different role: the golden data and
`make_hashmap.py` run in the SGLang image `dsv41-4x-spark:canary-roce`, built
by the MiaAI kit from its `Dockerfile.canary-roce`. That image is not part of
serving, and it is not on the boxes under that tag; the closest is
`lmsysorg/sglang:dev-dsv41`.

## 4. Defect: some requests never get a reply

### The error condition

A request is sent, the front-end accepts it, and no reply arrives. The engine's
own watchdog aborts the step at 120 s and rank 0 exits `rc 3`.

### The command that reproduces it

```bash

export DSGB10_ADDR=127.0.0.1 DSGB10_PORT=18893
export DSGB10_KEY_FILE=$HOME/dsgb10-data/dev-api-key
export DSGB10_ENGINE_ARGS="--max-ctx 1048576 --slots 16 --big-slots 4"
export DSGB10_FRONT_ARGS="--tokenizer $HOME/models/DeepSeek-V4.1-Flash-1017.deepseek-ai.FP8.safetensors.261018.v1/tokenizer.json --model-name deepseek-v4.1-flash"

K=$(cat $HOME/dsgb10-data/dev-api-key)
curl -s -m 150 -o /dev/null -w 'http=%{http_code} time=%{time_total}\n' \
```

### What was checked, and what each check ruled out

| check | result | ruled out |
| --- | --- | --- |
| GPU utilisation during the wait | `utilization.gpu` reads a constant 96 % even idle (0 % memory, 16.85 W). `dmon -s p` shows 16 W sustained during a freeze against 13 W for a request that answers | an idle wait: the GPU is busy, so the engine spins |
| which rank stalls | all 4 boxes draw above idle for the whole wait; `rank.1.log` to `rank.3.log` are empty | a dead rank, and a rank that never got the request |
| the gate or the collective after it | gate counters `held 0 in_flight 0 waiting 0`; the ring proxy shows `post=483` against `fromPrevA=486` in slot 0 | the gate; the wait is in a ring collective after it |
| README step 8 with and without the gate | `tf` and `k1` both exit 0 and print a hash; no service and no front-end in that path | the freeze being in the decode path in general |
| the prompt | `Count to five.` froze 8 of 8 in one batch, `pong` answered 8 of 8 in the same batch, but `Hello` answered at 11:38 and froze at 11:20 | the prompt as a stable cause |
| the engine arguments | README defaults `--max-ctx 262144` answered at 09:48 and froze at 11:20 with no change between | any single argument |
| the kept session on disk | removing the 32 GiB spill file did not help | stale spill state |
| memory | all 4 boxes had 118 GiB available during the freezes | memory pressure |
| the ring links | `ping` 0.8 to 1.5 ms; `roceP2p1s0f1` and `rocep1s0f1` `PORT_ACTIVE` | a broken link |
| the operator's local patch | stashing the 3 files and rebuilding reproduces the freeze (`500 120.355227`, `000 150.002410`, `500 1.561582`) | the local patch |

### Where the engine is blocked

Read with `ps -eo pid,comm`; a `pgrep -f` pattern matches the wrapper shell and
reports 1 thread, which is wrong. During a freeze the engine has 9 threads:

```
507017   dsgb10_rank      futex_do_wait
507020   cuda00001400006  poll_schedule_timeout.constprop.0
507032   cuda-EvtHandlr   poll_schedule_timeout.constprop.0
507033   dsgb10_rank      hrtimer_nanosleep
507434   dsgb10_rank      futex_do_wait
507435   dsgb10_rank      futex_do_wait
507452   dsgb10_rank      hrtimer_nanosleep
507453   dsgb10_rank      poll_schedule_timeout.constprop.0
507454   dsgb10_rank      futex_do_wait
```

Every thread waits on a futex, a CUDA event, or a sleep, and the main thread
waits on a futex. Combined with the 16 W draw, the picture is a spin loop that
keeps the GPU busy while the main thread waits for a signal that never comes.

### What is not bounded

I did not read the engine source to find the line that blocks. The repository's
`docs/` and its 8 open issues do not describe this symptom, and none of its 25
open pull requests names it. Issue #11 is the closest: it uses the same
`--max-ctx 1048576 --slots 16 --big-slots 4` configuration, but its symptom is a
50 s TTFT behind a long prefill and the request does answer.

The one test that would narrow it: the freezing path is the serve loop
(`kCmdSpecBatch` with drafts and multiple slots), and `k1` (`--mode decode`,
single session) does not freeze. A `--mode decode` run with `--spec` and 2 slots
would tell whether drafts or slots are needed.

## 6. What to do

The freeze belongs to this repository's author, not to the operator. The
evidence it needs is above: the reproduce command with the engine log. It hit
both chat encodings and every engine argument set tested, and it reproduced on a
clean build of `922dddb1`.

The checkpoint and encoding divergences are the operator's to decide. To run
step 8 as written, download `fb2764a5` (510 GB) and cut its rank files. To serve
`-1017` by the instructions, add `--encoding 1017` to `DSGB10_FRONT_ARGS`, which
`lossless-service.env` and `lossless-service-no-cf.env` in PROJECT ROOT now do.

A benchmark recorded against this build measures the speed of the `-1017`
checkpoint under the `v4.1` encoding, on a service that sometimes does not
answer. It is worth recording as a speed figure only, with those 3 facts stated
beside it.
